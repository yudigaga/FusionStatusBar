# FusionStatusBar 全项目优化计划

日期：2026-10-01。分析基线：源码版本 `0.3.129 / 143`。

执行状态：用户已授权实施除实机验证以外的计划，进度和交付结果见 [实施记录](optimization-implementation-20261001.md)。以下分析保留原始基线，实机验收条目本轮不执行。

## 1. 目标与判断

建议先解决编辑结果丢失、保存反馈不准确和运行时异常恢复，再改善跨进程配置、拆分职责和测量性能。保留现有 Java、原生 Android View 和 LibXposed API 102 技术路线，按功能逐步改造。

最终目标：编辑可恢复，配置是否生效可核对，异常能恢复原生界面，目标 HyperOS 版本上的表现有实机证据，每个发布版本都可追溯和回退。

本次查看了项目结构、主要配置与运行时调用链、核心编辑流程、测试及静态检查报告和近期修复文档。本次仅新增本计划，没有修改业务代码，没有重跑测试、构建 APK、安装设备或重新分析全部历史日志压缩包。

## 4. 分阶段实施

工作量按一名熟悉项目的开发者、有一台可持续测试的目标手机估算，共约 15-24 个开发日，通常需要 3-5 周。新增 ROM 适配和等待设备反馈另计；完成第一阶段后重新校准估算。

### 阶段 0：建立可回退、可核对的基线

优先级：P1。预计 1-2 日。

- 将当前源码纳入版本管理，记录已知可用版本与当前待验证版本；补充 README、构建要求、模块关系和支持范围。
- 重新执行现有测试、lint、构建，记录结果及工具链版本。当前 300 项测试作为回归集合，不把测试数量作为优化指标。
- 先锁定一组目标手机、Android、HyperOS、SystemUI、plugin 和 LSPosed 版本，记录控制中心、状态栏及通知中心的现有表现。
- 将 Gradle 设为版本唯一来源，生成 Hook 日志常量和 Xposed 元信息；发布校验覆盖版本、签名、APK SHA-256 和源码版本。
- 为外围 APK、日志和反编译材料建立索引及后续归档约定，先保留原始证据。新增构建产物放入 `artifacts/releases/<version>/`，按设备/日期关联日志与截图。

验收：可按文档从源码构建；发布清单能区分源码版本、APK 版本、实际注入版本和实机验证范围；已有可用 APK 与原配置有恢复路径。

### 阶段 1：修复数据可靠性与异常恢复

优先级：P1。预计 4-6 日。依赖阶段 0。

- 提取 `ControlCenterEditorSession`，集中管理正式基线、草稿、当前模式、选中项和有界撤销历史。通过独立草稿存储恢复进程重建后的编辑，不因保存草稿而发布配置。
- 持久化接口返回成功或明确失败；仅在写入成功后更新已保存基线，失败继续保留未提交状态和撤销记录。
- 对回退、解绑、停止监听、释放应用磁贴分别实施异常隔离和必要的 finally 清理；一次失败不能阻止其余资源释放。
- 核对 Hook 安装和 observer 注册状态，分别记录尝试、成功与失败。重试按具体注册项执行，避免重复安装已成功的 Hook。
- 能力统计以实际成功的 Hook 句柄为准，区分必需方法与可选方法；全局材质 Hook 成功不能代表控制中心布局 Hook 可用，电池适配缺失也不应阻止独立的时钟功能安装。
- 增加配置、布局版本迁移及异常输入回归；继续保留现有数量、大小和几何校验。

验收：

1. 编辑后旋转、切换主题、重建 Activity 或模拟进程回收，草稿和模式可恢复；正式配置在点击推送前保持原值。
2. 注入写盘失败时不提示已保存，不丢失草稿；重试后读回内容与提交内容一致。
3. 注入某个 OEM View 恢复异常，后续监听和磁贴资源仍完成释放，异常不逃逸到 SystemUI 主线程，重复清理安全。
4. 注册失败后有界重试能恢复，已成功的 Hook 不重复注册；缺少必需布局方法时不会报告控制中心完整可用。

### 阶段 2：完善配置和预览协议

优先级：P1/P2。预计 3-5 日。依赖阶段 1 的可靠保存接口。

- 配置使用递增修订号，分别表达草稿、已持久化、SystemUI 已读取、各功能已应用或降级；把加载的模块版本、目标 ROM 信息和失败原因纳入回执。
- 配置加载与写盘使用有界串行后台任务，合并连续变更，丢弃过期结果；主线程只切换已解析快照并更新视图。IPC 卡住时保留最后可用状态，避免无界创建线程或堆积任务。
- 推送超时显示等待或失败状态，保留已保存版本，不能误报为系统已生效。未显示的控制中心可报告等待挂载，实际挂载后再确认应用结果。
- 为预览补充 request/clear/ready 交错、旧请求迟到、写入中断和多调用方测试。将截图写入按 generation 隔离的临时文件，完成后原子发布文件与元数据的关联。
- 预览按目标显示尺寸后台解码；相同 generation 复用结果，回调校验当前会话和请求，明确 Bitmap 的释放时机。
- 保留 Provider 的现有鉴权，补充未授权访问和 Direct Boot 场景测试；限制截图、图标与布局数据的大小和保留数量。

验收：旧回调不能覆盖新请求，清空后旧截图不会重新出现，读者不会读取半个 PNG；快速连续提交最终应用最新修订；主线程不再执行上述磁盘读写与完整截图解码；“已保存”和“已应用”均有独立证据。

### 阶段 3：按真实职责整理结构

优先级：P2。预计 4-6 日。逐个模块合入，不进行全量改写。

| 拟整理的模块 | 负责的行为 | 接口原则 |
| --- | --- | --- |
| 编辑会话 | 草稿、撤销、模式、导入、发布基线 | 页面提交编辑动作并读取会话状态 |
| 配置存储与同步 | 迁移、校验、持久化、修订号、应用回执 | 隐藏 SharedPreferences、Bundle 和线程顺序 |
| 实际预览 | 请求、采集、发布、缓存、取消与失败结果 | 对页面暴露完整的一次采集结果 |
| OEM 宿主适配 | 类/方法探测、Hook 安装、plugin loader 差异 | 返回明确能力及不可用原因，按实际 ClassLoader 管理 |
| 控制中心运行时 | 布局挂载、原生状态恢复、磁贴资源生命周期 | 挂载与释放成对，异常结果可测试 |
| 设置页面 | 状态栏、遥测、通知中心、控制中心、概览页面 | MainActivity 保留导航和生命周期协调 |

- 沿用 `ControlCenterLayoutPlan`、几何、材质、时钟和遥测等已有模块，优先减少多个调用方需要共同维护的状态。
- 热路径反射结果按实际 Class/ClassLoader 缓存；已探测不存在的能力也缓存，避免反复抛异常。未知宿主保留对应原生功能并记录能力缺失。
- 为挂载、释放、提交建立稳定的包级行为入口，逐步减少测试对私有类名、字段和构造函数顺序的依赖。
- 随模块迁出清理 JADX 合成方法、全限定类名和重复刷新；一次编辑事务合并为一次必要的渲染更新。
- 先在现有 app 模块内整理包和职责。等依赖方向稳定后，再评估是否值得拆 Gradle 模块。

验收：新增某一功能的参数或某一 OEM 差异时，主要改动集中在所属模块；Activity 和 Hook 入口主要协调调用；现有行为与像素回归保持通过。代码行数只辅助观察，不作为拆分成功标准。

### 阶段 4：性能、交互和发布验收

优先级：P2。预计 3-5 日。性能采样在阶段 0 建基线，本阶段按结果优化。

- 分别测量应用与 SystemUI 的 CPU、内存、帧耗时及后台唤醒；记录冷/暖启动、连续开合、编辑和推送场景，避免把其他进程的日志归因于本模块。
- 重点观察 `requestLayout`、画布重建、布局重复解析、绘制分配和反射查找次数。优先优化已测热点，并保留前后对照。
- 评估运行时仅为布局实际使用的磁贴创建 record，并减少高频摘要和诊断输出；保留原生编辑和资源恢复所需的数据。
- 保留遥测后台线程和熄屏跳过重采样逻辑；进一步评估熄屏取消定时轮询、亮屏重建基线，以及秒级时钟在不可见状态下停止刷新。
- 检查状态栏宽度分配、长时钟、双 SIM、Wi-Fi/蜂窝切换、充电、横竖屏、锁屏和主题变化；温度/天气源不可用时稳定显示不可用状态。
- 为控制中心编辑补齐重做、明确的未保存/等待应用/失败状态、草稿恢复入口；按收益逐项交付。配置备份与布局预设可放到后续版本。
- 审查字体放大、深浅色、触控目标、图标可读性和无障碍操作；中文文案集中到资源。保留现有页面结构，优先修复实际操作阻力。
- 在独立变更中验证 AGP/Gradle/JDK/LibXposed lint 组合；固定图标资源来源提交和 Gradle 分发校验和。对必要的 OEM 反射作有依据的局部抑制。
- 发布命令串联单测、lint、打包、签名和版本核验；记录尚未通过的实机项目。完成目标设备验收后再标记该设备可用。

验收：

1. 同设备、同布局、同刷新率做开关模块对照和优化前后对照，每类核心开合场景至少采样 30 次，保留帧耗时分布、慢帧和录屏。
2. 帧预算按实际刷新率制定，例如 60 Hz 为约 16.7 ms、120 Hz 为约 8.3 ms；具体改进目标在基线采样后确定，不预设未经测量的提速百分比。
3. 重复进入/退出编辑和展开/收起后，无持续增长的挂载对象、监听或应用磁贴资源；没有本模块导致的崩溃或原生界面无法恢复。
4. 模糊 0/50/100、卡片/磁贴/组合项目、开合动画、原生编辑、禁用恢复及 SystemUI 重启均通过目标真机检查。
5. 每次发布记录支持范围、已知问题、测试结果和恢复方法；未验证机型明确标记为未验证。

## 6. 范围取舍

- 本轮优化重点是已有功能的可靠性和维护成本；先完成阶段 0-2，再决定是否增加新的视觉效果和布局能力。
- 继续使用现有 Java 与 View 技术路线，当前没有足够收益支持同时迁移 Kotlin/Compose 或引入大型依赖注入框架。
- 不以清空全部 lint 警告、追求更高测试数量或压缩某个文件到固定行数为目标。
- 首先支持已具备设备验证条件的 ROM 组合，随后按兼容报告增加适配；minSdk 并不代表所有厂商 ROM 已通过验证。
