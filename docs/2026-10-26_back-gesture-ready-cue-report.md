# 返回停顿就绪提示与误返回修正

日期：2026-10-26。用户明确第二段震动用于提示“可以松手触发”，并反馈距离、等待时间不稳定且容易误返回。本报告修正 0.5.18 将第二段放在动作提交点的理解；旧版本报告保留为历史记录。

## 确定性复现

实际调用 `LauncherBackHoldGesture.install` 的模拟宿主，经过指针 Hook、开始回调和结束回调。首次 10 项测试有 6 项失败：按住 500 ms 没有第二段反馈；顺序实际为原生取消→反馈→动作；已就绪后的小幅边界回撤失去执行资格。编译成功，测试断言失败。红色 XML 和命令日志保存在 `E:\vs\claude\xtjm\analysis\back-gesture-ready-cue-20261026\red` 与相邻 `back-gesture-ready-cue-red-20261026.log`。

按可验证性排序的候选解释为：反馈绑在 UP 而非 READY；严格原生进入门槛同时用于退出及完成判断；单一 touchSlop 和缺少等待意图阶段让抖动重新计时、提前松手落回系统返回。它们支持本地修复，不作为全部真实设备异常的唯一原因。

## 状态和时间规则

1. 原生接受输入后，只有配置完整的自定义动作才参与等待。进入距离调用当前宿主的 `isShowBackArrow(float)`，契约缺失时保留既有回退。
2. 手指在抖动半径内停稳 100 ms 后，预检动作是否可用；成功后捕获等待意图。此后提前松手取消原生返回，避免等待未完成时退回上一页。READY 前明显移动会解除本次等待并重新计时，持续侧滑仍可返回。
3. 停稳满 500 ms 再次预检，就绪锁存并立即发出第二段反馈。这里只检查可用性，不执行动作。定时以 MotionEvent/Handler 共同的 uptime 安排绝对截止时间。
4. 松手只消费已提示状态；重新准备新鲜动作，先完成原生取消清理，再执行。原生 finish=false 本身不足以推翻就绪，因为它也可能仅表示坐标小于原生进入距离。
5. CANCEL、多指、明显回撤或配置变化仍取消；真实松手时间早于就绪提示也不能执行。已提示后不再依据迟到的旧移动历史追溯重置，当前坐标仍可明确撤回。

进入后 pending/READY 分别允许 12/24 dp 的回撤带；抖动半径为 max(touchSlop,16 dp)。这些是本轮确定的默认交互规则，没有宣称来自手机数据统计。不同屏幕密度使用相同 dp 换算。

可用性预检返回的 Runnable 不保存、不调用，避免长按超过签名时效后使用旧 Intent。松手时重新准备。State 和定时任务仅持有 View 弱引用，代次控制撤销旧任务，使用宿主手势 Looper。

计时优先使用收到指针回调的 Looper，让就绪和抬手串行；仅缺失时回退 View/Main Looper。可用性检查返回后再次核对代次和终止状态，避免检查过程中发生重入抬手后补发旧提示。两种情况均有实际安装 seam 的回归用例。

原生箭头在重新显示时会清除 feedbackDone，可能在第二段之后再次发送 Ready 反馈。新增可选的精确 `GestureBackArrowView$1.onAnimationSuccess(Animator)` Hook，在已提示的同一箭头上恢复反馈标记，再完整调用原生回调一次；不修改通用震动服务。弱标记保持至下一 DOWN，覆盖结束后迟到回调。宿主契约缺失时此辅助 Hook 独立降级，不影响主要停顿和绘制 Hook。
